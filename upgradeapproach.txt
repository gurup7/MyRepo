The application's EJB layer, currently authored to the EJB 2.0 specification, comprises 4 Stateless Session Beans and 14 Message-Driven Beans, with no Entity Beans (CMP/BMP) present as confirmed by the AMA scan. Accordingly, the recommended approach is an in-place upgrade to Jakarta EE 10 (EJB 4.0) on IBM WebSphere Liberty rather than a JPA rewrite. This involves a javax.ejb → jakarta.ejb namespace migration for Session Beans and a javax.jms → jakarta.jms change for MDBs (which are re-pointed to IBM MQ), enabled by Liberty's enterpriseBeans-4.0, mdb-4.0, and messaging-3.1 features. This is a minor, tool-assisted change (Eclipse Transformer / OpenRewrite) with no structural refactoring of business logic. The detailed bean-level inventory, per-component change assessment, and effort estimates are captured in the accompanying analysis workbook [reference: EJB Analysis tab, <filename.xlsx>].

For 4.2.7 — Hibernate Migration Approach
Persistence is currently handled by Hibernate 5.4.31 using the native SessionFactory API and HBM XML mappings (not JPA-annotated entities). The recommended approach is a mandatory two-hop upgrade (5.x → 6.x → 7.x), as a direct 5→7 jump is unsupported. This upgrade addresses the flagged BlackDuck/CVE vulnerability and aligns with the Java 21 and Spring Framework 7.x targets. Key considerations include the javax.persistence → jakarta.persistence namespace shift, the removal of the legacy Criteria API and save()/update()/saveOrUpdate() methods, and several silent runtime behavior changes (ID generation, query result types) that necessitate data-layer integration tests prior to the upgrade. The detailed call-site inventory, HBM mapping assessment, and version-compatibility matrix are captured in the accompanying analysis workbook [reference: Hibernate Analysis tab, <filename.xlsx>].
