What the existing program does

The current Java program classifies each job into one of two target outcomes based solely on the date_conditions field:

date_conditions: 1 (fixed schedule) → OpenShift Jobs
date_conditions: 0 (no fixed schedule) → remains on Autosys
While this is a useful starting point, using a single field produces some classifications that may need a closer look:

Jobs with date_conditions: 0 are frequently dependency-triggered (e.g., condition: s(FEED_CHK)) or started by their parent BOX. These are fully automated and are strong candidates for OpenShift, yet the current logic labels them as "remains on Autosys."
Some jobs with date_conditions: 1 (e.g., WebLogic/NGINX start and stop jobs) may not need to move at all, since OpenShift manages container lifecycle natively.
Additional considerations I built into an enhanced script

To validate the classification more thoroughly, I put together a lightweight script (dependency-free, so it runs without any package installation given the proxy restrictions) that classifies each job into four target categories, each with a justification column:

ELIMINATED — jobs no longer required on OpenShift (e.g., app/web server start-stop and sleep jobs), since Deployments and health probes manage lifecycle natively.
Autosys Only — jobs tightly coupled to non-containerized/on-prem infrastructure (e.g., NDM transfers dependent on the on-prem VM) that should remain on Autosys until an SFTP bridge is validated.
OpenShift Job — on-demand or dependency/BOX-triggered jobs that run once when invoked.
OpenShift CronJob — jobs with their own recurring schedule (native CronJob, or Argo CronWorkflow where internal dependencies exist).
Decision order applied (top-down, first match wins)

Lifecycle jobs (server/web start-stop, sleep) → ELIMINATED
NDM / on-prem coupled jobs → Autosys Only
Jobs with an independent schedule (start_times) → OpenShift CronJob
Standalone jobs with date_conditions: 1 → OpenShift CronJob
Jobs with a condition: dependency → OpenShift Job
BOX-triggered jobs (date_conditions: 0) → OpenShift Job
Default (on-demand) → OpenShift Job
This approach evaluates functional category, dependencies, schedule, and infrastructure coupling — with date_conditions used as a supporting signal rather than the sole determinant.

Why this matters

The goal is to ensure our target-platform decisions and effort estimates are dependable before we apply them across all ~500 jobs, and to give each classification a clear, auditable justification for the blueprint.
